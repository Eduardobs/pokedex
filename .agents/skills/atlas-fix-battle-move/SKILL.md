# Fix a battle move

## Required inputs

Receive both inputs from the request:

- **Move name:** a localized name or canonical PokéAPI slug.
- **Expected behavior:** a description of what the move should do, including the conditions and interactions supplied by the user.

Example: `$atlas-fix-battle-move Golpe: Lunar Blessing. Comportamento esperado: curar o status do usuário e recuperar um quarto do HP máximo, sem aumentar evasão.`

If either input is missing, ask for that input before changing behavior. Resolve the name to a unique canonical slug and ID using repository data; clarify any remaining ambiguity rather than guessing a similar move.

## Establish the correction

Read [project context](../../PROJECT_CONTEXT.md) before changing the project and preserve its invariants. Inspect the working tree and retain unrelated changes.

Consult **both** `docs/battle-move-audit.md` and `docs/battle-move-audit.json` before implementing. Locate the move by ID/name and read its findings, verified scenarios, reference requirements, supplemental behavior, and format exclusions. Compare the requested behavior with existing tests and bundled references under `src/data/third-party/`.

Follow the audit's generation policy: modern main-series rules, bundled Showdown definitions, and documented singles exclusions. If the request conflicts with these rules or a lasting project definition, explain the concrete conflict and clarify whether an intentional exception is requested before implementing it. Consult primary sources when bundled evidence is insufficient and record the applicable generation and source for reviewed reference changes. Do not refresh every snapshot merely to fix one move.

## Implement and verify

- Trace parsing and supplements in `src/lib/battle-data.ts` and `src/lib/battle-move-effects.ts`, then execution in `src/lib/battle.ts` and relevant specialized modules such as `src/lib/battle-multistrike.ts`. Correct the responsible layer rather than only changing descriptions or audit verdicts.
- Add deterministic regression coverage in relevant battle tests that fails for the original defect and asserts the expected observable result. Cover applicable failure conditions, costs, timing, probabilities, and requested interactions; control randomness.
- Keep tests offline with existing fixtures and bundled data. Preserve other moves sharing the handler and cover them when the change risks a regression.
- If descriptions or logs change, update supported locale catalogs under `src/i18n/locales`. Add a lasting project-wide definition to `.agents/PROJECT_CONTEXT.md` only when the request establishes one.

## Update both audit documents

`docs/battle-move-audit.md` and `docs/battle-move-audit.json` are generated by `src/lib/battle-move-audit.test.ts`; multistrike coverage also participates through `src/lib/battle-multistrike.test.ts`.

1. Update the report generator and scenario mapping as needed so findings and `verifiedScenarios` describe scenarios actually exercised by regression tests. Retain unresolved interactions. Baseline invariants or the presence of a handler do not certify full correctness.
2. Run focused regressions, then `npm run audit:battle-moves` to regenerate **both** documents. Do not rely on manual report edits that regeneration would erase.
3. Review the generated diff. Markdown and JSON must agree on identity, behavior, verified scenarios, and limitations. Preserve full audited ID coverage and unrelated findings. Change the reference hash only when the underlying reviewed reference changes.
4. Run `npm run check` for the implementation change. Report failed or unavailable checks accurately; never record unexecuted scenarios as verified.

Finish with the canonical move and ID, corrected behavior, regression coverage, updates to both audit documents, and remaining limitations.
