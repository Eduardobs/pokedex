# Performance audit

Date: 2026-11-13. Baseline: the working tree before this change, with no local modifications. Both builds use the same installed dependencies and build environment. Measurements below describe code size and deterministic work counts, not browser latency or Core Web Vitals.

## Findings and changes

| #   | Cost observed                                                                                              | Change applied                                                                               | Before → after indicator                                                                                                |
| --- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 1   | Moves UI is statically imported by the detail route.                                                       | Load `PokemonMovesTab` with `React.lazy` and a loading fallback.                             | Included in route → separate 6.57 kB chunk requested on first use.                                                      |
| 2   | Technical data, history and sprite gallery are in the detail route's eager dependency graph.               | Load `PokemonDataTab` on selection.                                                          | Included in route → separate 11.11 kB chunk.                                                                            |

| 4   | An inactive moves tab still mounts and computes versions, groups and filtered lists.                       | Mount it on its first visit; retain its instance for the current Pokémon when changing tabs. | One initial moves mount → zero until selected.                                                                          |

| 9   | Version sorting repeatedly splits resource URLs inside its comparator.                                     | Parse each unique version ID once before sorting.                                            | Two URL parses per comparison → one per unique version.                                                                 |

The detail route chunk decreases from **66.30 kB to 47.74 kB (28.0%)**, or **19.79 kB to 15.24 kB gzip (23.0%)**. These are individual chunk sizes; shared dependencies and the full application are not reduced by the same percentage. The initial index chunk changes from 266.52 to 266.67 kB as the bundler redistributes shared code. Stat-array reads decrease by **94.3%**. The sorting fixtures count actual accesses rather than asserting unstable timing thresholds.

## Other opportunities identified

- `useIntersectionVisibility` creates one observer per off-screen card. A shared observer per root margin could reduce observer instances. Retained pending a browser profile that demonstrates material overhead and tests for multi-target cleanup.
- `PokemonMovesTab` renders every compatible move in every method group. Progressive disclosure could bound DOM growth for Pokémon with large learnsets. Retained because it requires a separate interaction decision and keyboard/accessibility validation; requests already wait for card visibility.
- Large lazy map chunks remain (Paldea: approximately 477 kB) and model-viewer remains approximately 1,025 kB. They already load on demand. Further splitting requires measurements of map navigation and 3D usage rather than moving bytes between chunks without reducing work.

## Reproduction and regression coverage

Run `npm run build` and inspect the `PokemonDetailPage`, `PokemonMovesTab`, `PokemonDataTab` and `PokemonEncounters` lines. Run `npx vitest run src/lib/performance.test.ts src/lib/pokemon-sort.test.ts src/lib/move-learning.test.ts src/pages/PokemonDetailPage.test.tsx` for access-count, ordering, missing-data, duplicate-record, immutability and asynchronous tab navigation checks. The stat fixture uses 1,025 entries with value `(id * 7919) % 251`, sorted by descending total with ID ties; before this change, the comparator reads both stat arrays on every comparison.

The full required verification is `npm run check` (format, ESLint, coverage, Playwright and production build). The sandbox run passed formatting, lint and all 2,648 unit tests (121 files), with 87.46% statements, 82.41% branches, 88.41% functions and 90.49% lines. Its browser stage initially could not bind `127.0.0.1:4173` (`EPERM`); Playwright was rerun with permission to start the local server: all 232 browser tests passed. The final production build also passed. The additional detail-page test verifies that move preparation does not run before the tab opens and that its search survives switching tabs.

## Preserved behavior and tradeoffs

REST caching remains bounded at 250 entries with five-minute expiry and a 15-second request timeout. Request deduplication, cancellation, validation, CSP, error handling, translations, images, reduced-motion behavior and manual catalog pagination are unchanged. Sorting retains locale-aware comparisons, stable ties, missing values last, and input immutability. Move grouping retains every distinct method and level and the last reference for duplicate version names.

Opening a secondary tab for the first time now requires its chunk request and can briefly display the existing localized loading component. Sorting uses temporary O(n) label/value storage to remove repeated work; these structures are local to a call and are released afterwards. No new persistent cache or dependency is introduced.
